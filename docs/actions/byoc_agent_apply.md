# redpanda_byoc_agent_apply (Action)

Re-runs the Redpanda BYOC agent apply (`rpk cloud byoc <cloud> apply --redpanda-id=<id>`) against an existing BYOC or BYOVPC cluster, reconciling the agent VM and its network without changing the cluster. The cluster must be `STATE_READY`. Runs on the machine executing Terraform and needs that cloud's credentials the same way cluster creation does. Requires Terraform 1.14 or later. Invoke it ad hoc with `terraform apply -invoke=action.redpanda_byoc_agent_apply.<name>`, or trigger it from a resource lifecycle with `action_trigger`.

Use it when Redpanda asks you to re-run the BYOC agent apply on a cluster that already exists, for example to pick up a larger agent VM. The cluster itself is not modified and no Terraform state changes; a `terraform plan` after the action is empty.

The action runs the same plugin, with the same arguments and credentials, that `redpanda_cluster` runs while creating a BYOC cluster. Configure the provider's cloud credentials (`aws_*`, `gcp_project_id` and `google_credentials*`, or `azure_*`) or the matching environment variables on the machine running Terraform.

Terraform 1.14 or later is required for actions.

## Schema

### Required

- `cluster_id` (String) ID of the BYOC cluster whose agent to apply.

### Optional

- `timeout` (String) How long to wait for the plugin, as a duration such as `45m`. Defaults to 45m.

## Example Usage

```terraform
# Declare the action once. The cluster id comes from a variable rather than
# from redpanda_cluster.prod.id on purpose: a before_update trigger on the
# cluster runs ahead of the cluster, so an action config that reads the
# cluster's attributes forms a cycle and Terraform refuses the plan.
variable "prod_cluster_id" {
  type = string
}

action "redpanda_byoc_agent_apply" "prod" {
  config {
    cluster_id = var.prod_cluster_id
    timeout    = "45m"
  }
}

# Ad hoc, when Redpanda asks you to re-run the agent apply on an existing
# cluster (the equivalent of `rpk cloud byoc aws apply --redpanda-id=...`):
#
#   terraform apply -invoke=action.redpanda_byoc_agent_apply.prod
#
# Or apply the agent before every change to the cluster, so the cluster
# change runs through an up-to-date agent:
resource "redpanda_cluster" "prod" {
  name              = "prod"
  resource_group_id = redpanda_resource_group.prod.id
  network_id        = redpanda_network.prod.id
  cloud_provider    = "aws"
  region            = "us-east-1"
  zones             = ["use1-az1", "use1-az2", "use1-az4"]
  throughput_tier   = "tier-1-aws-v3-arm"
  cluster_type      = "byoc"
  connection_type   = "private"

  lifecycle {
    action_trigger {
      events  = [before_update]
      actions = [action.redpanda_byoc_agent_apply.prod]
    }
  }
}
```

Run the action once, without applying any other change:

```shell
terraform apply -invoke=action.redpanda_byoc_agent_apply.prod
```

To run it ahead of every change to the cluster, put a `before_update` trigger on the cluster as in the example and pass the cluster id in through a variable. An action config that reads `redpanda_cluster.<name>.id` cannot be triggered before that same cluster: Terraform reports a cycle, because a before-event trigger has to complete before the resource it would read from is planned.

## Preconditions

The action refuses to run, at plan time when `cluster_id` is already known, when:

- the cluster is not a BYOC or BYOVPC cluster
- the cluster is not `STATE_READY`; a `STATE_FAILED` cluster is reported with its failure description, since a fresh agent does not resume a failed cluster
- the provider lacks the GCP project or Azure subscription the plugin needs for that cloud

AWS credentials are resolved by the plugin from the usual AWS credential chain and are not checked ahead of time.
